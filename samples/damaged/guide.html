samples/damaged

Eleven damaged files, and which keys to press

One walkthrough per sample: the command that opens it, then the TUI keys in the order they are worth pressing, and what each one puts on screen. Every count, message and timing here was measured against these files by driving the interface, not read off the source.

Rebuild the samples with .venv/bin/python samples/build/makedamaged.py and samples/build/makepcap.py. Commands are written as toeknife; use .venv/bin/toeknife if the venv is not active.

How the keys work

Every printable character fills a hole, because typing the byte you think belongs somewhere is the point of the tool. Commands therefore live on ctrl and function keys, and nothing you type while solving can trigger one.

On the tape

← → ↑ ↓move the byte cursor; home/end row ends, pgup/pgdn page
tab / shift+tabnext / previous unknown class
any characterfill the hole under the cursor and every position equal to it
ctrl+xfill with a hex byte instead

ctrl+z / ctrl+rundo / redo; a whole model run undoes as one step
ctrl+n / ctrl+pnext / previous back-reference

ctrl+ggo to an output position (negative numbers allowed)
ctrl+w / ctrl+swrite recovered bytes / save the session
ctrl+kthe menu: every command, including the ones with no key

Colour is provenance

  • green — literal, read straight from the bitstream
  • cyan — copied from a byte that is already known
  • yellow — your guess, or a byte one of your guesses implies
  • magenta — a model fill, or a byte one of them implies
  • red ░ — unknown and fillable
  • grey ░ — window space no back-reference reaches

Green and cyan are facts. Yellow is something you asserted. Magenta is something a model suggested. Red is a question. Four kinds of claim, four colours, and they never mix.

with no corpus, f4 and ctrl+f have little to go on

With no --corpus at launch and no f5, the model is trained on the stream's own recovered bytes, and on a small stream that is not enough to clear the default 99.5% floor. ctrl+f then reports model filled nothing: nothing above 99.5% confidence, which is the tool being honest. Every walkthrough below runs this way: the payload is payload.txt, and a corpus holding it would hold the answer. Measured numbers for exactly this are in the preset-dict.zlib walkthrough.

A freeform path in f5 is resolved against the directory you started toeknife in, and the picker shows what it found before anything is committed, so a path that points nowhere says 0 file(s) instead of silently doing nothing.

the checksum is on f8

The status bar carries the container's verdict as one word — crc ok, crc MISMATCH, adler ? — and f8 opens the whole of it: what the wrapper recorded, what this decode produced, and what the checksum can still pin. It is the only thing on screen that separates a right recovery from a plausible one, and half the samples below are interesting because the tape looks perfect and that one word does not.

--verify on the command line prints the same verdict, which is still the right way to check an exported file.

evidence.zip · rotted.md

One flipped bit. The stream inflates to exactly the right length and 64 bytes of it are wrong. This is the walkthrough for what damage looks like when nothing on screen can tell you about it.

inspection, nothing to fill 96,000 B out, 0 holes CRC says otherwise

Before you open it

toeknife samples/damaged/evidence.zip
toeknife samples/damaged/evidence.zip --entry rotted --verify
rotted.md: size 96000/96000 ok  crc 6da73ded/8d7c5e32 MISMATCH
FAILED: the decode does not match what the container recorded.

Then

toeknife samples/damaged/evidence.zip --entry rotted

  1. read the status bar

    out 0  block #0 dynamic  96000 bytes  no holes  floor 99.5%  crc MISMATCH  end

    Everything else on that line says the recovery went perfectly: 96,000 bytes, no holes, a clean end-of-stream. Every byte on the tape is green or cyan, which is to say a fact read off the bitstream or copied from one. The container disagrees.

  2. f8the whole verdict

    what the container recorded
  zip: rotted.md
  size   96,000 bytes
  crc32  8d7c5e32

what this decode produced
  96,000 bytes, 96,000 known, 0 unknown class(es) over 0 position(s)

verdict
  size 96000/96000 ok  crc 6da73ded/8d7c5e32 MISMATCH
  FAILED: the decode does not match what the container recorded.
  Every byte decoded, so some bytes read from the bitstream are wrong.
  ctrl+k "fill from a suspected copy" shows where they differ from a copy.

    The right number of bytes came out, so only the checksum noticed. esc to go back.

  3. f4the model has no job here

    It refuses, and the refusal is the information:

    nothing unknown left to fill

    There is nothing unknown to fill. The damage is not a hole, it is a wrong answer wearing a right answer's colours.

  4. ctrl+g 29390the first wrong byte

    In a real case you would not know this number. It is here so you can see what the damage looks like from inside.

  5. read the bits pane

    The cursor sits on a back-reference, and the pane on the right takes it apart field by field:

    match 13,6292    bit 100345..100368   reads 23098..23110
  litlen code    sym 266 length base 13   code 1110110
  length extra   +0 → length 13
  dist code      sym 25  dist base 6145   code 1010
  dist extra     +147 → distance 6292

    The flipped bit is bit 100360 (byte 12545, bit 0 of the compressed data), inside that eleven-bit distance extra. Undamaged, the same symbol reads match 13,6300: the same codes, plus 155. One bit moved the copy's source eight bytes.

  6. enterfollow the copy to its source

    The cursor jumps to output 23098, where the tape reads r sir,” cri. Those thirteen bytes are real text from earlier in the file, copied legally by a legal match into a position where , my dear sir belonged. Eleven of them differ. Later matches copy the wrong bytes onward, which is how one bit becomes 64 wrong bytes spread from 29390 to 74991.

  7. ctrl+bthen esc

    The blocks pane confirms there are two dynamic blocks and both headers parsed cleanly. Nothing structural is wrong with this file.

the point

Nothing in the view marks position 29390. The copy is well-formed, its source is real, and the colour scheme calls it cyan because it is a copy of a known byte. The status bar knows the file is wrong, from 32 bits of arithmetic in the central directory; it cannot know which of the 96,000 bytes is the lie. Bit rot inside a block header is the other case, and bitrot-header.gz is that one.

evidence.zip · shredded.md

200 bytes of the compressed data replaced with garbage. The decode does not stop, it drifts: 64,637 correct bytes, then 61,426 wrong ones, still 96.9% printable.

inspection, nothing to fill 130,019 B out of a recorded 130,000 size and CRC both wrong 
toeknife samples/damaged/evidence.zip --entry shredded --verify
toeknife samples/damaged/evidence.zip --entry shredded
shredded.md: size 130019/130000 MISMATCH  crc ae6697a7/2dc67a69 MISMATCH

  1. read the status bar first

    out 0  block #0 dynamic  130019 bytes  no holes  floor 99.5%  size MISMATCH  end

    end means the decode reached a final block and stopped cleanly. It is nineteen bytes longer than what the ZIP recorded, and the status bar leads with the size rather than the checksum because the length is already wrong — there is no need to compute a checksum to know this one failed. f8 spells it out.

  2. ctrl+g 64637the seam

    Text before the cursor is The Adventures of Sherlock Holmes. Text after it is what a Huffman decoder produces once it is a few bits out of step:

    sticking up a station from time to time, or stopping the wagL anon byra one
elsenly fastweenhave ave ave atake me oyour “Td the tl yournl-holda tall you my
cortall ter whte

  3. ctrl+nwalk the back-references

    The first match after the seam is at output 64638, match 3,9401. It reaches over 9 KB back into text that is correct, and copies it into a place it does not belong. That is why damage spreads instead of staying local.

  4. ctrl+wwrite it out anyway

    Half of this entry is genuine. Export it, then compare against whatever else you have; the tool will not pretend to know where the good part ends.

evidence-noeocd.zip and evidence-sfx.zip

The same five entries, arriving two ways that break an ordinary reader. Both are command-line stories; once an entry opens, the view is identical to the two walkthroughs above.

container layer only
toeknife samples/damaged/evidence-noeocd.zip
! no end-of-central-directory record: the archive is truncated, or this is
  only a piece of one
! recovered 5 entries by scanning for local headers; sizes may be missing for
  streamed entries

All five entries come back, and --entry rotted --verify still reports the same CRC mismatch, because the local header carries its own copy of the checksum.

toeknife samples/damaged/evidence-sfx.zip
EOCD at 105944: 5 entries, central directory 279 B at 101569
offsets are shifted by +4096 bytes (prepended data, or a truncated front)

4096 bytes glued to the front. The shift is measured rather than guessed: the EOCD says how large the directory is and where the file ends, and the difference is arithmetic. Entries verify afterwards.

capture.gz

Three members, the second damaged 40 bytes into its deflate data: 60 bytes inverted inside the dynamic header, so the table that defines every symbol in that member is gone. This walkthrough ends in a refusal, and the refusal is the right answer.

member 1 is unrecoverable members 0 and 2 verify 
toeknife samples/damaged/capture.gz
member 0 at 0: OS Unix, mtime 0
member 1 at 16672: OS Unix, mtime 0, deflate data did not decode (bad-table)
member 2 at 36959: OS Unix, mtime 0
! member 1 did not decode; the walk picked up again at member 2 (offset 36959),
  the next gzip header found by scanning whose data decodes to its end

gzip records no compressed length, so the end of a member is found by decoding to it. One member that will not decode takes the position of every member after it, and the fallback is to scan for the 1f 8b magic. A header found that way is taken only when its data decodes to its own end, and member 1's CRC32 and length are read from the 8 bytes in front of it.

toeknife samples/damaged/capture.gz --entry 1

  1. what opened

    out 0  0 bytes  stopped at 0  floor 99.5%  size MISMATCH  bad-table

    Nothing, from a 50,000-byte member. The header that builds the table is the damaged part, so not one symbol after it can be read.

  2. f7what next, before trying anything

    The top row is repair the header: try every one-bit flip, because a header that fails with its bits present is what bit rot looks like. Below it, each route to a lost table is marked available or says why it is not. enter on the top row:

    632 of 632 1-bit flips over 632 header bits: nothing parsed cleanly. Either
the damage is not in this span or it is more than 1 bit(s).

Two flipped bits are 199,396 pairs over these 632 bits: about 55 s at this
search's rate. The recorded checksum still picks the one that is the original.

    enter again tries the pairs. It took 25 seconds here:

    199,396 of 199,396 2-bit flips over 632 header bits: 10 parse, and none
matches the recorded size and checksum. The damage is elsewhere or more than
2 bit(s).

    Ten pairs make a header that parses, and the best of them decodes 268 bytes. The CRC32 read from the 8 bytes in front of member 2 rules out all ten. 480 bits were inverted, so no small flip search was ever going to find it. esc leaves the data alone.

  3. f3scan for a boundary

    Eleven candidates over the whole member. Read the last column, not the counts:

        bit     byte  kind     blocks  out  holes  recovered
  86427   10,803  dynamic       1   21      0  lIl·␑UgImhoZleUol[ee␁
   5755      719  dynamic       1   10      0  ··········
 115590   14,448  dynamic       1    8      0  ·!␚····␑
 107970   13,496  dynamic       1    6      0  ·␐␚␒·␔
  84099   10,512  dynamic       1    3      0  ·,·

  4. escreject all eleven

    Each row is a dynamic header that parsed out of noise and built a legal-looking table before its body fell over. The best is worth 21 bytes of junk. Stored-block headers fire on noise too, and a stored block "decodes" whatever follows it, so the scan keeps a stored candidate only when the stream carries on correctly after it. None does here. The preview column is still the check worth reading.

  5. ctrl+qand go where the data still is

    toeknife samples/damaged/capture.gz --entry 0 --verify   # verified, byte for byte
toeknife samples/damaged/capture.gz --entry 2 --verify   # 60,000 B, verified

    Member 1's table was in the damaged bytes, and this member had no flush markers to carry another one. The damage cost exactly one member, and the tool says so instead of dressing up a few bytes of noise as a recovery.

read this way

The resync list is sorted by how much each boundary recovers. That ranking is advisory. The previews are the evidence, and here they overrule the sort order completely.

preset-dict.zlib

A zlib stream compressed against a 40-byte dictionary the file does not carry. Other tools refuse it. Here the missing dictionary becomes 28 unknown bytes, and this is the sample to learn the solving keys on.

28 classes over 1,608 positions 19,200 B out, 17,620 known Adler-32 available 
toeknife samples/damaged/preset-dict.zlib
opening the only DEFLATE entry: zlib stream
toeknife: zlib stream: compressed against preset dictionary 3fb40f8b, which is
not in this file: references reaching into it become holes
no corpus here, on purpose

The payload is payload.txt, so a corpus holding it would hold the answer, and nothing else on the machine carries these 40 bytes. Opened with no --corpus, the predictor reads self-trainedx0.881 + table priorx0.25, its best proposal is 95.2%, nothing is marked ✓ at the default floor, and ctrl+f answers model filled nothing: nothing above 99.5% confidence.

Dropping the floor does not rescue that. At 0.95 it fills one class and it is wrong; at 0.60, three, all wrong; at 0.25, sixteen, ten of them wrong. A preset dictionary is a word list, and the model trained on this stream's prose has no way to guess one.

  1. where the cursor lands

    out -38  dictionary  19200 bytes  28 holes / 1608 slots  floor 99.5%  adler ?  end

    Output position −38. The dictionary occupies −40 to −1, and the tape opens on the first hole in it. The 28 classes are not 28 bytes of output: they cover 1,608 positions, because every reference into the dictionary joins the class of the byte it reads.

  2. tab shift+tabwalk the classes

    28 stops, not 1,608. That ratio is the whole reason for the representation.

  3. ctrl+g -23 then type fthe biggest class

    set 'f' at -23, and 288 positions equal to it

    One keystroke, 289 cells. They turn yellow, and so does everything a later copy derives from them.

  4. backspaceor ctrl+z

    cleared guess at -23, and the hole count goes back to 28. Use ctrl+x instead of a character when the byte is not printable.

    Clear it before moving on. A guess is context for everything the model does next, so a wrong one left lying around costs fills: with f still sitting at −23, ctrl+f at a 25% floor fills twelve classes and gets one right, against sixteen and six without it. The true byte there is a space.

3 · MODELS YOU BUILT EARLIER: ~/.toeknife/models

4 · BYTE MODEL

    The title line says what the picker is for: A corpus of the wrong KIND is worse than none: -17.2 bits per byte against -8.0 for knowing nothing. Section 3 lists every model found in ~/.toeknife/models; section 2 fetches on a second enter and caches under ~/.toeknife/corpora. The ⌨ type a path instead… row takes anything, and a path there is resolved against the directory you launched toeknife from. The first enter only looks, so a path that points nowhere says so before anything is committed:

    train on what you named
  no such file or directory: nowhere-at-all
  0 file(s), 0 bytes
  nothing readable there

    None of these holds the dictionary, and the one file here that holds the stream's text is the answer itself. esc backs out, and the rest of this walkthrough stays self-trained.

  6. f4read before accepting

    28 open classes, 0 at or above the 99.5% floor (✓). Context is from each
class's most readable occurrence.

      -38   x6    ' '   95.2%   't' 0x0a '.' 'n'    to love for I[ ]░░e Adler. All
      -11   x3    ' '   94.6%   ',' 'f' 'e' 'a'     The Red-Head[ ]░░League·   II
      -5    x7    ' '   69.3%   't' 'e' 'n' 'a'   ediately outs░[ ]░ the door. Th

    x6 is how many positions that class covers. The context column is the text around the class's most readable occurrence, so the suggestion can be read in place. Read it here: the dictionary at −38 is r, and the model's surest answer is a space.

  7. - - - +move the threshold and watch the ✓ move

    99.5% →  0 at or above
99%   →  0
95%   →  1
90%   →  2

    The rungs are 0.999, 0.995, 0.99, 0.95, 0.90, 0.80, 0.70, 0.60, 0.50, 0.25, 0. Whatever you leave the dial on is what ctrl+f uses afterwards, and the status line shows it as floor.

  8. ctrl+atake every ✓

    accepted all at or above 95%: 1 class(es) filled, ctrl+z undoes the lot

    Holes fall from 28 to 27. The filled bytes come back magenta, so a model's suggestion never gets mistaken later for something you knew. This one is wrong. ctrl+z puts it back.

  9. ctrl+fthe same job with propagation, and a stop

    Stopped before filling the dictionary

1 class(es) clear the 95% floor, but each holds a byte of the preset
dictionary. A dictionary is a list of common strings, and the floor was
measured on running text: fills there measured 48% right at an 80% floor.

The dictionary itself proves every byte at once. The program that wrote this
stream usually holds it.

Nothing has been filled.

d find the dictionary in a file   enter fill anyway   esc stop here

    Every hole in this file is a dictionary byte, so ctrl+f asks first. d looks for the dictionary in a file you name, which is the route that proves every byte at once. enter fills anyway:

    model filled 1 classes (6 positions), surest first, down to 95% in 1 rounds;
ctrl+z undoes the lot

    At the default 99.5% it answers model filled nothing: nothing above 99.5% confidence without stopping. The message names the floor rather than claiming the model has nothing, and f4 shows what it does have.

  10. f8let the checksum have an opinion

    The status bar has read adler ? since the file opened: a checksum over output that still has unknown bytes is not evidence, and the tool will not pretend otherwise. The panel says what it can still do:

    what the checksum can still do
  Adler-32 only: two sums modulo 65521. It cannot be solved like CRC32, but it
  still rules candidates out.
  enter shortlists each unknown byte with the model and keeps only the
  combinations that reproduce the checksum. Survivors are counted and shown:
  five unknown bytes under Adler-32 alone once produced a wrong answer that
  checksummed correctly.
  There is no model loaded to shortlist with. f5 gives it a corpus.

    Press enter and it refuses, and says why:

    checksum: the checksum cannot finish this on its own (no CRC32 recorded for
this stream), and there is no model to shortlist with. Press f5 for a corpus,
then try again

    That refusal is the honest answer for this file. ctrl+l alternates the model and the checksum until neither moves, and here it moves nothing: 0 of 28 classes filled over 1 round(s), 28 left; not checked against a checksum. The ledger distinguishes refused to rule from found nothing, which is the whole difference between a check that could not run and a check that ran and cleared it.

  11. ctrl+wthen check it outside

    toeknife samples/damaged/preset-dict.zlib --verify

    Same verdict, from the command line, for an exported file.

Then let the checksum have an opinion

toeknife samples/damaged/preset-dict.zlib \
         --solve --solve-confidence 0.70 --checksum-solve --verify
solver: filled 0 of 28 classes (0 output positions) in 0 rounds; stopped
because the 2 classes left above 70% hold bytes of the preset dictionary, a
word list rather than text, where fills measured 48% right. 28 classes still open.

The command line stops at the dictionary the same way. With --fill-dictionary and a 0.25 floor it fills sixteen classes, and the checksum still declines for want of a model to shortlist with. Adler-32 cannot say which byte is wrong. It can refuse to bless an answer it cannot check, which is more than the tape can do on its own.

capture-head.bin + capture-tail.bin

Two pieces of one stream with 2,048 output bytes missing between them: a capture that lost packets. The gap is set up on the command line, then the view opens on the seam.

2,048 classes over 11,335 positions 60,000 B out, 48,665 known 
toeknife samples/damaged/capture-head.bin \
         --gap samples/damaged/capture-tail.bin --total-size 60000
gap: the tail after the loss starts with a block header of its own, which
     decodes cleanly to the end; it is read from there
gap: output gap of 2,048 bytes, from the recorded decompressed size

The tail was cut at a flush, so it opens on a block header and carries its own table, and it is read from that header. Without --total-size it searches, and gets this one wrong: 709 bytes against the true 2,048, with 6,097 bytes reading across the gap to judge by. It says that much itself:

gap: gap of 709 bytes, the best of 8,193 tried (6097 bytes read across it); a
     search result, which nothing here proves
gap: it scores 1.09, against a median of 1.07 over 200 gaps sampled; that
     barely stands out, so the gap may be past the 8,192 searched (--gap-max)

  1. where the cursor lands

    out 8192  60000 bytes  2048 holes / 11335 slots  floor 99.5%  end

    Output 8192, the first byte of the hole, because the head decodes exactly 8 KB. Mode reads assembled.

  2. ↓ ↓ pgdnlook at the shape of it

    2,048 missing bytes cover 11,335 unknown positions, so on average each class turns up about five and a half times, the rest of them copies further down the stream. Fill one and it lands in all of them.

  3. ctrl+fand read why it stops

    Stopped before filling inside long unknown runs

1 more class(es) clear the 99.5% floor, but every occurrence of them sits in a
run of 256 or more bytes that nothing was read from -- a lost packet, or a gap
that size. Fills there measured 19% right whatever the floor, because each one
becomes context for the next and the model ends up agreeing with itself.

Nothing has been filled.

enter continue anyway   esc stop here

    About seven seconds to get here. enter continues:

    model filled 1 classes (1 positions), surest first, down to 99.5% in 1 rounds;
ctrl+z undoes the lot

    One byte out of two thousand, and it is wrong. A 2 KB hole in the middle of prose is not something statistics reconstruct. ctrl+z takes it back.

  4. ctrl+wthe part worth having

    48,665 bytes on either side of the hole are exact. That is the point of the gap machinery: get the offset right and everything else is correct, get it wrong and the cross-gap copies silently read the wrong text.

carved-midblock.bin

60 KB carved out of the middle of a stream written with no flushing at all. The table is behind the damage and the next one is a long way off. This is the sample that shows the tool's limits.

1 byte as opened 80,813 B after f3, 8,787 classes 
toeknife samples/damaged/carved-midblock.bin

  1. what opened

    out 0  block #0 fragment  1 bytes  stopped at 1  floor 99.5%  bad-dist

    One byte, read from bit 12. Nothing is wrong with the tool; the bits at the front of this file are the middle of a symbol stream whose table is gone.

  2. f7what could be tried

    The top row is scan for the next block header (f3), with the reason: the decode stops after 1 bytes: a carve that starts inside a block has no table, and the next header carries its own. Below it, two routes run (decode what is here, scan for a boundary), two ask for something (a related capture, known plaintext), two are marked as not in this release (the 1,828-table and 89,247-table dictionary sweeps), and the rest do not apply, each with its reason: no header here to repair, the block's end is not known, no known plaintext, no dynamic block to gate.

the comparison worth making

Open samples/streaming-fragment.bin --resync next. A similar carve, written with a sync flush every 8 KB: 42,861 bytes known instead of 13,910. How the stream was written decides almost everything, and this sample exists to make that difference visible.

  1. open it and read the status bar

    toeknife samples/damaged/plot-damaged.png --entry 0
    out 0  block #0 dynamic  28880 bytes  no holes  floor 99.5%  adler MISMATCH  end

    The chunk CRC in the listing told you where the damage is. The zlib Adler-32 sits at the end of the pixel stream and covers the output, so it is the one that says whether a recovery is right, and it is the one in the status bar. f8 shows both numbers.

  2. ctrl+nthen enter

    toeknife samples/damaged/plot-damaged.png --entry 0

    The first back-reference is at output 2066; enter follows it to 804. Binary data renders as Control Pictures (␀␁␂…␡), one cell per byte, so matches and literals still line up column for column even with nothing readable on the tape.

  3. f6more room

    Hides the blocks pane. On a narrow terminal that is the difference between seeing a 200-byte match and seeing forty bytes of one.

  4. f5 → the png rowthe corpus trap

    These 28,880 bytes are filtered scanlines, not the PNG file's bytes. Training on .png files as they sit on disk trains on compressed noise, so that row carries ⚠ inflated first and the scan decompresses before it trains. The catalogue's Wikimedia entry in section 2 is the same thing fetched rather than found.

  5. f7 then enterrepair it with the chunk CRC

    The top row is repair flipped bits with the chunk CRC. A chunk CRC covers the compressed bytes, so one or two flipped bits can be solved for:

    ONE REPAIR, PROVEN TWICE.
chunk 2 of 2: byte 200 bit 6.

Flipping it back restores the chunk's CRC32 over the compressed bytes and the
stream's Adler-32 over the decoded ones.

3 flip(s) restore a chunk CRC; 1 also match the Adler-32.

    Three flips satisfy the chunk CRC on its own, and the Adler-32 picks one of them. enter applies it and the status bar reads adler ok.

plot-splitrun.png is the structural sibling: undamaged, but with a tEXt chunk between the two IDATs, which the spec forbids. The listing warns that the run is not consecutive; the pixels still verify, because this file interleaves rather than losing anything. The warning matters for the file where it has lost something, which decodes to nonsense somewhere without ever failing.

toeknife samples/damaged/report-noxref.pdf --entry 1

  1. ctrl+binto the blocks pane

    Arrow through the dynamic header: BFINAL, BTYPE, HLIT, HDIST, HCLEN, the code-length code, then the literal/length and distance tables in full. Every field still points at the bits it came from.

  2. enter on a blockthen esc

    Selecting a block sends the cursor to the first byte that block emitted. The two panes track each other in both directions: move the cursor and the pane opens whichever block produced the byte under it.

  3. ctrl+n enter ctrl+pread the compressor's decisions

    On a clean stream this is a bitstream inspector rather than a recovery tool. enter on a match highlights the bytes it copies from, which is the terminal version of hovering over it.

  4. f2refused, correctly

    alignment picker applies to fragments only

    This stream starts at a block header, so there is no alignment to choose. The refusal is worth seeing once so the distinction between f2 and f3 sticks.

Suggested order

If you are showing this to someone, or reminding yourself what the tool does, four samples cover the range:

#samplewhat it teaches
1evidence.zip · rotteda decode that succeeds and lies, and the checksum that notices
2preset-dict.zlibholes as equality classes, the corpus, the confidence dial, undo
3capture.gz --entry 1reading previews instead of scores, and a refusal that is the right answer
4carved-midblock.binhow the stream was written decides everything, and which question each scan answers

Two things worth carrying out of all of them. The status bar's one word is the only thing on screen that separates a right recovery from a plausible one, and it can say a file is wrong without being able to say which byte. And every screen that ranks something is sorting a list, not making a decision: the previews, the context columns and the plan panes are where the evidence is.
